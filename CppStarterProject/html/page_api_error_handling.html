API Error Handling

An introduction to error handling in the HaptX SDK.

Motivation

The HaptXApi error-handling scheme is motivated by three desires:

  1. The desire to return by value directly (i.e., a function named GetFoo() should return a Foo object).
    • The HaptX API follows modern C++ guidance and returns most values directly—using move semantics and copy elision to guarantee performance—rather than relying on out parameters.
  2. The desire to supply an error code in the event of an API failure.
    • The HaptX API consolidates all of its error codes into a single enumeration: HaptxApi::ReturnCode. All APIs that can return an error will return a value from this enumeration.
  3. The desire to make checking for an error as simple as checking a bool return type.

Result<T>

These three desires listed above are somewhat contradictory. How do you return a value and an error code simultaneously, while making error-checking the same as a bool check?

C++23 provides the answer in the form of std::expected . However, since the HaptX SDK's minimum requirement is C++17, it uses tl::expected instead.

Note
tl::expected is just a back-ported version of std::expected that works with the HaptX SDK's minimum compiler versions.

The result is HaptxApi::Result<T> , which is just a typedef for tl::expected<T, HaptxApi::ReturnCode>.

For those unfamiliar with std::expected, it can be thought of as an std::pair containing both an expected value (type T, in our case) and an unexpected value (our error code) that is returned instead, in the case of an error. Unlike an std::pair, since it is specialized for this use-case its semantics for error-handling are well-defined.

Note
The T parameter can be void (and void is, in fact, the default value of T) if the API in question does not return a non-error value. This is seemingly redundant, but it enables more natural error-handling semantics.

If the APIs returned a ReturnCode directly, checking for an error would require checking that the result was ReturnCode::SUCCESS , which has a value of 0 (false, once converted to a boolean!), which would be the opposite of every other API, and a source of confusion and errors.

Checking for errors

A Result<T> can be cast to a bool to determine the success or failure of the API function. If the result is true, the API was successful.

// Given:
HaptxApi::Result<> ExampleFunction();
// Check for API success
if (ExampleFunction()) {
// API was successful
}

If the cast result is false, the API call failed. The ReturnCode can be accessed with .error(). E.g.,

auto ret = ExampleFunction();
if (!ret) {
// API call failed; get error code with .error()
HaptxApi::ReturnCode error = ret.error();
}

Note
The auto keyword is preferred for capturing the return value of a HaptX API function, to avoid having to specify lengthy template names.

The above code can be simplified slightly using C++17's if-statement syntax:

if (auto ret = ExampleFunction(); !ret) {
// API call failed; get error code with .error()
HaptxApi::ReturnCode error = ret.error();
}
Note
Capturing the result inside an if-statement is preferred, when possible, because it scopes the return value's variable name.

Accessing the return value

If the type of T is non-void, it can be accessed with .value() if the API was successful. Also, operator* is equivalent to .value(), and operator-> can be used to directly dereference the value, similar to how smart-pointers classes (like std::unique_ptr ) are implemented.

// Given:
HaptxApi::Result<std::vector<int>> ExampleFunction2();
if(auto ret = ExampleFunction2()) {
// API call was successful
// Access the value using .value()
std::vector<int>& value = ret.value();
// Access the value using operator*; this is equivalent to the above
// statement in this context.
std::vector<int>& value2 = *ret;
// Using operator-> to directly access members on the returned std::vector
size_t size = ret->size();
} else {
// API call failed
HaptxApi::ReturnCode error = ret.error();
}
Note
You must only call value() on successful results, and only call error() on unsuccessful results. Attempting to retrieve the value of an unsuccessful result—or the error code from a successful result—may result in a thrown exception (for value() or error()) or undefined behavior (for operator* or operator->).

Similarly, you must not call value() on a result that does not return a value, i.e, when the T in Result<T> is void.
