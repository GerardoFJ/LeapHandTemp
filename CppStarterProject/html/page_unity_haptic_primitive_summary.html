Unity Haptic Primitive Summary

Descriptions and recommended use of Unity Haptic Primitive classes.

See Unity Haptic Primitives for low-level documentation.

Notes before we start

A Haptic Primitive is any interaction in a game world that contains at least one HxJoint or child component of it.

We highly recommend disabling grasping on dial-like interactions. This can be accomplished with an HxPhysicalMaterial Script on the dial GameObject , and is done for you on templates available in our game plugins.

HxJoint

HxJoint is the core class from which all Haptic Primitives are based. It is built upon ConfigurableJoint and adds features that make it easier to design and build complex interactions. These features include:

  • Non-spring physical models
  • Custom physical behaviors in constraint space
  • Custom state management in constraint space
  • Angular magnitudes above 180°
  • Linear limit offsets
  • The ability to UpdateJoint settings without reforming the constraint
  • The ability to Freeze and Unfreeze the joint without affecting other settings
  • The ability to add forces/torques directly to anchors rather than bodies
  • The ability to teleport anchor1
  • The ability to enable/disable the joint without deleting the component

The HxJoint class gives developers greater control over their interactions by providing multiple layers of customizable and parallelizable classes. See Table 1 for a list of all base classes and Figure 1 for an example of how they appear in the Inspector .

Constraint space

HxJoint s and all related classes operate in constraint space.

The concept of constraint space can be confusing the first time you encounter it. It works like this:

  • A joint forms a constraint between anchors attached to two Rigidbody objects.
    • Anchor2 gets defined as the scaled position of anchor in body2's space and it has the rotation defined by axis and secondaryAxis also in body2's space.
    • Anchor1 gets defined as the scaled position of connectedAnchor in body1's (aka connectedBody ) space.
    • Anchor1's rotation always matches anchor2's rotation when execution starts (Figure 2, Left ).
    • These anchors are fixed with respect to their bodies so long as the joint exists.
  • Constraint space gets arbitrarily defined as the space described by anchor2's frame, making body2 the "parent" and body1 the "child".
    • The position and rotation of anchor1 frame with respect to anchor2 frame at any point (keeping in mind that both are able to move around the world, Figure 2, Right ) get used to drive every calculation inside of the HxJoint .
    • See Table 2 for a summary of all elements involved in this calculation.
    • Check the Visualize Anchors property in the Inspector to visualize this relationship in real-time.

See Figure 3 for an example of a button translating in the constraint space -X direction as defined by the orientation of the joint, not either of the constrained components. See Figure 4 for a similar example of a rocker switch rotating in the constraint space -X direction.

Note
If the autoConfigureConnectedAnchor property is true, then the value of connectedAnchor will be automatically calculated to match the initial world position of anchor. This is useful when creating angular joints or other joints that are expected to have anchors co-located at the beginning of the game.

If the configuredInWorldSpace property is true, then the rotations of anchor2 and anchor1 are defined by axis and secondaryAxis in world space instead of body2 space. The positions of anchor2 and anchor1 remain unchanged. This is useful when creating lots of joints that need to operate in the same frame and you don't want to worry about what the initial values of the joined rigid-bodies' rotations are.

# Element Description

3 Anchor1 frame The space described by anchor1
4 Body2 The second constrained rigidbody (parent)

HaptxPrimitiveDebugger

The HaptxPrimitiveDebugger prefab is included in the plugin to make using and debugging HxJoint easier. Add one to your scene by spawning the prefab located in the HapticPrimitives folder of your plugin installation, or by manually adding the component to an existing GameObject . Set the value of the Target Game Object field to the GameObject that owns the HxJoint you're trying to debug and the HaptxPrimitiveDebugger will show you position information for each HxDof, as well as the current states of any HxStateFunction found on any HxDof .

Hx1DTranslator and Hx1DRotator

Many interactions only operate in one degree of freedom and do not require the full power and flexibility of HxJoint s. For these simpler interactions we recommend using Hx1DTranslators or Hx1DRotators. These classes maintain the features of HxJoint in the degree of freedom that they operate in and add additional parameters for convenience. These parameters include:

  • Initial position
  • Lower positional limit
  • Upper positional limit
  • Damping

The Damping value gets passed to the relevant ConfigurableJoint property based on how the constraint is configured, so it only applies to motions of the rigid-bodies with respect to each other. Contrast this to Rigidbody damping which applies to the gross motion of a rigid-body in the world.

HxDof

The HxDof class represents a single degree of freedom and brings together sets of HxDofBehavior s and HxStateFunction s. It includes functions that allow HxDofBehavior s and HxStateFunction s to be found by name (Unity Haptic Primitive Summary), as well as a function that returns the current constraint space position along its degree of freedom (Listing 2). Note that HxDofs will only be updated by their associated HxJoint s if they have at least one behavior or state function, or their Force Update flag is set to true.

Listing 1

// Listing 1. Finding HxStateFunctions and HxDofBehaviors by name.
// The HxJoint object is a component like any other.
HxJoint joint = GetComponent<HxJoint>();
// Each HxJoint owns an HxDof object for each cardinal degree of freedom.
HxDof dof = joint.GetDof(DegreeOfFreedom.X_LIN);
// Each HxDof object owns HxStateFunctions and HxDofBehaviors that can be
// referenced by name.
HxStateFunction stateFunction;
dof.TryGetStateFunctionByName("Function0", out stateFunction);
HxDofBehavior dofBehavior;
dof.TryGetBehaviorByName("Behavior0", out dofBehavior);

HxDofBehavior

The HxDofBehavior class represents a physical behavior that operates in a single degree of freedom (see HxDof). The class contains many features, but its primary purpose is to produce a desired physical behavior through the application of forces or torques based on the constraint space position along its degree of freedom. See Table 3 for the types of HxDofBehaviors included in the plugin and their desired behaviors. The full list of features includes:

  • Varying the underlying HxPhysicalModel
  • Optionally applying accelerations instead of forces/torques
  • Enabling/disabling the behavior at runtime
  • Visualizing the applied forces/torques or accelerations for debugging

If a behavior requires stabilization, you may match a positionDamper field to the behavior's degree of freedom using the Configurable Joint Parameters field in the Inspector . For example, to stabilize behaviors in the X-Linear degree of freedom, increase the value of Configurable Joint Parameters → X Drive → Position Damper .

Note
When using Hx1DTranslators or Hx1DRotators the value of the Damping field automatically populates the corresponding positionDamper .

Behavior Type Description
HxDofDefaultBehavior Produces a behavior about the resting position (0.0). Most useful when combined with a HxCurveModel to define the entire force/torque profile for a degree of freedom.
HxDofTargetPositionBehavior Produces a behavior about a target position.
HxDofDetentBehavior Mimics the mechanical behavior of detents. See relevant section for more detail.
Table 3. Types of HxDofBehavior.

HxDofDetentBehavior

This class is inspired by detents, which are small hitches in motion commonly used to add haptic feedback to volume dials, multi-position toggle switches, and other devices.

Functionally, HxDofDetentBehaviors are similar to HxTargetPositionBehaviors except that rather than always driving about a single target position they dynamically drive about the position of whichever detent is nearest (in constraint space ), which may change based on the positions of the constrained bodies.

The class exposes a Detents array in the Inspector for defining which positions in constraint space position constitute detents.

HxPhysicalModel

HxPhysicalModels are simple classes that represent models that HxDofBehavior s can use to drive about target positions. They are given the constraint space distance from any arbitrary target position described by the HxDofBehavior , and they output the signed magnitude of the force that should be applied to the Primitive based on the model they represent. See Table 4 for a list of the default models included in the plugin.

Model Description
HxConstantModel Generates a constant restoring force/torque
HxSpringModel Generates a spring force/torque
HxCurveModel Generates the force/torque defined by a given AnimationCurve
Table 4. Types of HxPhysicalModel.

HxStateFunction

HxStateFunctions break constraint space down into integer states, and fire their OnStateChange events every time their states change.

Custom classes may bind these events to perform any in-game logic or actions that are desired as a result of changes in position (Listing 3). See Table 5 for a list of the default HxStateFunctions included in the plugin.

Class Name Description
Hx2StateFunction Divides constraint space into two states at a given transition position
Hx3StateFunction Divides constraint space into three states at given low and high transition positions
HxNStateFunction Divides constraint space into N states where any given position is associated with the nearest transition position
HxCurveStateFunction Each constraint space position is associated with the rounded output value of a given AnimationCurve
Table 5. Types of HxStateFunction.

Listing 3

// Listing 3. Binding OnStateChange.
// Setup HxStateFunction logic at the beginning of the game.
void Start () {
// The HxJoint object is a component like any other.
HxJoint joint = GetComponent<HxJoint>();
// Each HxJoint owns an HxDof object for each cardinal degree of freedom.
HxDof dof = joint.GetDof(DegreeOfFreedom.X_LIN);
// Each HxDof object owns HxStateFunctions that can be referenced by name.
HxStateFunction stateFunction;
if (dof.TryGetStateFunctionByName("Function0", out stateFunction)) {
// Each HxStateFunction has an OnStateChange event that fires whenever its
// state changes.
stateFunction.OnStateChange += HandleStateChange;
}
}
// Game logic that occurs whenever our HxStateFunction changes state.
void HandleStateChange(int newState) {
switch(newState) {
case -1:
// Logic here.
break;
case 0:
// Logic here.
break;
case 1:
// Logic here.
break;
default:
// Logic here.
break;
}
}
